# راه‌اندازی HIM & I و دریافت APK

## نکتهٔ مهم

گیت‌هاب کد را نگه می‌دارد و GitHub Actions فایل APK می‌سازد؛ **جای سرور دائمی و پایگاه‌دادهٔ چت نیست**. یک APK روی هر دو گوشی نصب می‌شود و هر نفر حساب خودش را می‌سازد. ظاهر هر حساب مستقل است.

APK با نام `setup-debug` عمداً فقط صفحهٔ راه‌اندازی دارد. تا آدرس HTTPS و Supabase تنظیم نشده‌اند، این فایل را نسخهٔ دارای ورود/چت فعال حساب نکنید. هیچ حساب، پیام، تاریخ رابطه یا اطلاعات پریود ساختگی در آن وجود ندارد.

## ۱. پایگاه‌داده

1. با حساب خودتان در [Supabase](https://supabase.com/dashboard) یک پروژهٔ اختصاصی بسازید؛ منطقه و سیاست داده را آگاهانه انتخاب کنید.
2. در SQL Editor، همهٔ فایل‌های `supabase/migrations/` را به ترتیب نام اجرا کنید و سپس `supabase/seed.sql` را اجرا کنید. این کار را روی دیتابیس شخصی/پروژهٔ دیگری انجام ندهید. Seed فقط سؤال‌های بازی دارد، نه حساب و اطلاعات شخصی.
3. از تنظیمات API، آدرس پروژه و **publishable key** را بردارید. کلید **secret/service-role** جداست و فقط باید در تنظیمات محرمانهٔ سرور وب قرار بگیرد.
4. در Auth، ورود با ایمیل و تأیید ایمیل را فعال کنید. برای استفادهٔ واقعی دو نفر، SMTP و محدودیت ارسال ایمیل را بررسی کنید. رمز حداقل ۱۲ کاراکتر باشد.

هیچ کلید محرمانه، رمز دیتابیس، فایل امضای اندروید یا اطلاعات پریود را در چت، مخزن، Issues یا کامنت‌ها نفرستید.

## ۲. وب‌اپ دائمی HTTPS

این پروژه Next.js با API سروری است؛ GitHub Pages یا خروجی HTML ثابت به‌تنهایی کافی نیست. از میزبانی سازگار با Next.js مثل Vercel یا یک سرور Node استفاده کنید.

کد این کار روی شاخهٔ `arena/059cdeab-him-and-i` است، نه لزوماً شاخهٔ پیش‌فرض مخزن. در میزبان، همین شاخه را انتخاب کنید. راه جایگزین از کامپیوتر خودتان:

```sh
git clone --branch arena/059cdeab-him-and-i https://github.com/MGnoies12/him-and-i.git
cd him-and-i
npm ci
# برای Vercel، ورود و تأیید دسترسی را با حساب خودتان انجام دهید:
npx vercel
```

اگر هنوز آدرس ندارید، استقرار اول می‌تواند بدون تنظیمات و در حالت راه‌اندازی انجام شود تا آدرس HTTPS ثابت بگیرید. سپس در Environment Variables میزبان این‌ها را تنظیم و دوباره Build/Deploy کنید:

| نام                                    | مقدار و محل نگهداری                                       |
| -------------------------------------- | --------------------------------------------------------- |
| `NEXT_PUBLIC_SUPABASE_URL`             | آدرس HTTPS پروژهٔ Supabase، عمومی                         |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | کلید publishable؛ **نه secret/service-role**              |
| `NEXT_PUBLIC_APP_URL`                  | آدرس HTTPS نهایی وب‌اپ                                    |
| `SUPABASE_SERVICE_ROLE_KEY`            | کلید secret یا service-role، فقط در secret manager میزبان |
| `CRON_SECRET`                          | رمز تصادفی حداقل ۳۲ کاراکتر، فقط سرور/زمان‌بند            |

در Vercel بعد از تنظیمات و بررسی پروژه می‌توانید از `npx vercel --prod` استفاده کنید. این یک دستور برای اجرای آگاهانه توسط صاحب حساب است؛ این مخزن خودکار روی تولید Deploy نمی‌کند.

در Supabase Auth، Site URL را آدرس نهایی وب‌اپ بگذارید و `/auth/callback` و `/auth/confirm` را برای همان دامنه مجاز کنید. قالب ایمیل مناسب بازشدن روی مرورگر/گوشی دیگر در `DEPLOYMENT.md` آمده است. بعد از تأیید ایمیل در مرورگر بیرونی، در اپ هم وارد شوید؛ کوکی بین مرورگر و WebView خودکار منتقل نمی‌شود.

مسیر `/api/health` باید پاسخ `200` و `ready: true` بدهد. این فقط آماده بودن تنظیمات و دسترسی به شمای دیتابیس را بررسی می‌کند؛ جای تست واقعی ایمیل، چت و دو گوشی نیست.

## ۳. ساخت APK از GitHub Actions

1. در GitHub به **Settings → Secrets and variables → Actions → Variables** بروید.
2. یک **Repository variable** عمومی با نام `CAPACITOR_SERVER_URL` و مقدار آدرس HTTPS وب‌اپ بسازید؛ بدون مسیر، query یا نام‌کاربری/رمز. کلید Supabase یا service-role را داخل این متغیر نگذارید.
3. Workflow با نام **Android APK** روی push به شاخهٔ همین کار اجرا می‌شود. برای ساخت دوباره، پس از ذخیرهٔ متغیر:

```sh
git commit --allow-empty -m "build: rebuild configured Android [apk-release]"
git push origin arena/059cdeab-him-and-i
```

اگر workflow در شاخهٔ پیش‌فرض نیز ثبت شده باشد، می‌توانید از **Run workflow**، شاخهٔ همین کار، آدرس HTTPS و گزینهٔ `publish` استفاده کنید. تا قبل از آن، مسیر push بالا به ثبت workflow در شاخهٔ پیش‌فرض وابسته نیست.

4. بعد از موفقیت ساخت و lint، APK در Artifacts موجود است. پیام commit با `[apk-release]` یا انتخاب صریح `publish`، یک **Prerelease** برچسب‌خورده در Releases منتشر می‌کند و لینک دانلود مستقیم می‌دهد؛ هیچ merge یا استقرار تولیدی خودکار انجام نمی‌شود.
5. بدون آدرس وب، نام فایل شامل `setup` است. با آدرس، سلامت تنظیمات وب‌اپ قبل از ساخت بررسی می‌شود و فایل `configured-debug` تولید می‌شود.

فایل همراه `SHA256SUMS.txt` برای بررسی صحت دانلود و `build-info.json` برای نسخه/commit/نوع ساخت است. APKها و کلیدهای امضا وارد Git نمی‌شوند.

## ۴. نصب برای هر دو نفر

- اندروید ۷ به بالا (API 24). هر دو نفر **همان APK** را نصب کنند.
- برای نصب مستقیم، مجوز نصب برنامه از منبع دانلود مورداعتماد را در اندروید فعال کنید؛ هش فایل را بررسی کنید.
- هر نفر ایمیل و رمز مستقل داشته باشد. بعد از ورود، مشخصات و ظاهر خودش را انتخاب کند.
- تاریخ شروع آخرین پریود و طول معمول چرخه **اختیاری و فقط برای صاحب حساب** هستند؛ در اطلاعات Auth، کد دعوت یا صفحهٔ مشترک قرار نمی‌گیرند. برآورد، تشخیص پزشکی یا روش پیشگیری از بارداری نیست.
- یکی فضای دونفره می‌سازد و کد خصوصی را به نفر دوم می‌دهد؛ نفر دوم پس از ورود، کد را وارد می‌کند. کد یک‌بارمصرف و زمان‌دار است، ولی پس از اتصال، گفت‌وگو به حساب‌ها متصل می‌ماند.
- حالت ظاهری بر اساس انتخاب حساب پیش‌فرض می‌گیرد و قابل تغییر است؛ جنسیت مجوز خواندن دادهٔ دیگری ایجاد نمی‌کند.

نسخهٔ فعلی **debug-signed برای آزمایش نصب مستقیم** است، نه انتشار در Play Store. کلید debug در CI موقتی است؛ نسخهٔ ساخت دیگری ممکن است فقط بعد از حذف نسخهٔ قبلی نصب شود. برای به‌روزرسانی پایدار، کلید release باید در secret manager صاحب پروژه مدیریت شود، نه در مخزن یا چت.

## ۵. موارد جداگانهٔ لازم برای بهره‌برداری

- تست دو حساب و یک حساب نامرتبط روی سرویس واقعی: دعوت، چت، فایل خصوصی، لغو اشتراک‌گذاری و حذف حساب.
- زمان‌بند معتبر برای **POST** به `/api/jobs/reminders` با Bearer `CRON_SECRET`. یادآورها و پاکسازی فیزیکی فایل‌ها بدون آن خودکار اجرا نمی‌شوند.
- Web Push به VAPID نیاز دارد. تحویل native APNs/FCM هنوز به آداپتور سروری و تست دستگاه نیاز دارد؛ نصب APK یا گرفتن توکن به معنی تحویل اعلان نیست.
- پروژه‌ها و تنظیمات میزبانی/SMTP با حساب صاحب محصول ساخته می‌شوند. اتصال گیت‌هاب به‌تنهایی مجوز ساخت حساب یا پذیرش شرایط این سرویس‌ها نیست.
- راهنمای امنیت، دادهٔ سلامت، نگهداری/پشتیبان و محدودیت‌ها در `SECURITY.md`، `DEPLOYMENT.md` و `MOBILE.md` است.
